A Flask → FastAPI migration agent whose verifier is not a language model. Writing the new code is the easy half — a model does it in eight seconds. The hard half is earning the right to merge it.

Read the last row again. The new code is better. It is also a different contract, and every client with retry-on-5xx behaves differently tomorrow. A migration is not allowed to improve behaviour any more than it is allowed to break it — and no reviewer reading that diff would have stopped it.

Why the obvious design fails

A model cannot be the oracle for its own output

The natural build is: migrate with a model, then ask a model to write tests for the result. That verifier is worthless — and worse than worthless, because it is confident. The tests are generated from the migrated code, so they encode whatever the migration decided. Change {"error": …} to {"detail": …} and the generated test asserts detail. Green.

The specification has to come from somewhere the model does not control. Here it already exists, and it is still running: the legacy application itself.

01Read the routes — parse the Flask source with ast, never execute it. Recovers decorators, add_url_rule, and Flask-RESTful resources.no model
02Derive the probes — happy path, missing field, wrong type, malformed JSON, absent id, wrong method, bad query type, unauthenticated.no model
03Record the contract — run the original app in a sandbox and store how it answers every probe. This is the specification.no model
04Migrate — analyst writes a risk brief, migrator writes the FastAPI module.model
05Replay and diff — the same probes against the new app; compare status and normalised body.no model
06Repair — an agent receives the behavioural diff, inspects probes, greps the original, tests candidates.model
07Approve — nothing is written to disk until a person says so.human

Steps 1, 2, 3 and 5 contain no model at all. That is the design, not an implementation detail.

The agent

One repair, turn by turn

Taken verbatim from the committed trajectory for case_14 — fifty lines of real third-party code from flask-restful. Baseline scored 33%. Five model calls and 132 seconds later, 100%.

TURN 1

Read the failures it was handed

The differential gives it a behavioural diff, not a traceback. It opened three probes in a single turn.

→ get_probe_detail(r00.POST.wrong_method) ← legacy: 405 {"message": "The method is not allowed for the requested URL."} candidate: 405 {"detail": "Method Not Allowed"}
TURN 2

Formed a hypothesis, then went looking for it

Three searches of the legacy module for the error text. All three came back empty.

→ search_legacy("KeyError") ← no matches → search_legacy("browser") ← no matches → search_legacy("Method Not Allowed|…") ← no matches

This is the interesting moment. Those strings are in the responses and nowhere in the application. A fixed pipeline has no move here — the agent had to conclude something.

TURN 3

Changed strategy, correctly

→ search_legacy("add_resource|Resource|request\.form") ← 12: from flask_restful import Resource, Api 15: api = Api(app) 45: todos[todo_id] = request.form['data']

It worked out that the error envelope belongs to Api(app) — the framework wrapper — not to the application code. Which is exactly why grepping the module for the message found nothing.

TURN 4

Wrote a candidate and tested it before committing

→ run_differential(<complete module>) ← {"run": 1, "budget_left": 2, "parity_strict": 1.0, "matched": 9, "probes": 9}

Full parity on the first candidate. The loop stopped rather than spending its remaining turns.

The line that makes the point

return JSONResponse({"message": "Internal Server Error"}, status_code=500)

The legacy app raises an unhandled KeyError and surfaces a 500. The baseline migration tidied it into a 404. The repair agent put the 500 back — not because it was told to preserve 500s, but because the old app answered 500 and the old app is the specification. An agent checked by a model would have been congratulated for the 404.

What the 212 probes are made of

A reviewer should know the shape of the denominator before reading a percentage, so here it is.

Probe kindCountShareWhat it asks
happy5726.9%a valid request, the answer the clients depend on
wrong_method4521.2%a verb the route does not serve
absent_id4219.8%a path parameter that does not exist
missing_field188.5%a body with a required key removed
bad_type188.5%a field of the wrong type
malformed_json188.5%a body that is not JSON at all
unauthenticated104.7%the request without its credential
bad_query_type41.9%a query string the handler will try to cast

Two things follow that work against the headline number, and both are worth saying out loud rather than leaving in the code.

41% of the set is wrong_method and absent_id — the two classes cheapest to get right, because they mostly ask the framework to reject a request rather than asking the application to compute an answer.

26% of probes, 55 of 212, are scored on their status code alone. Those are the ones where the legacy app replied with Flask’s own HTML error page. The exemption is deliberately narrow: parity.py requires a 4xx/5xx status and an HTML content type, so a CSV export, a plain-text response and an HTML page served with a 200 are all compared in full. It was wider once — an earlier version relaxed the check for any non-JSON body and quietly stopped comparing 8 of 13 probes on one case.

So “100% parity” means: every probe reproduced the legacy status, and every probe whose body the legacy app actually authored reproduced that body too. It does not mean the tool reproduced Flask’s error markup, which no FastAPI migration can or should.

Not one model, from either vendor, in any generation, got a single piece of real third-party code right on its own.

Three things fall out of that table, and none of them is "use a better model".

Capability does not predict safety. Model strength moved the baseline between 1 and 12 out of 16 without ever moving the column that matters. The reasoning model did not beat the fast model it costs three times as much as.

What that deliberately does not say is that the cheaper model is better — see the replication below, where the ordering reverses.

Most failures are not crashes. The third column counts migrations that imported cleanly, served every route, answered every request — and answered differently. Across the five baselines that is 36 migrations. On the two DeepSeek models it is every single failure: nothing there would have been caught by checking that the app boots.

Verification amplifies capability; it does not replace it. The repair loop improved all five, but it only reached 16/16 on models strong enough to act on a diff. gpt-4o-mini writes Pydantic v1 syntax and unterminated f-strings; being told precisely what is wrong does not make it able to fix it. An oracle tells you the truth about your migration. It cannot write the migration for you.

Verify it

Two paths, depending on how much you want to spend

The point of the project is that a claim should be checkable, so this one is too.

Path A — no AI at all <1 min · $0.00

No API key. No network. Everything that decides correctness here is deterministic, so all of it can be checked with the models switched off.

# 49 tests, no model involved
docker compose run --rm test

# the full five-variant ablation, from the committed cache
docker compose run --rm reproduce

These models are not deterministic even at temperature 0, so a live re-run produces different numbers and nobody could check the reported ones. Every request was recorded instead — turning four dollars and six hours of model time into twenty-three seconds.

It cannot cheat. A prompt missing from the cache raises CacheMiss and stops the run with a non-zero exit. Truncate the cache and watch it refuse:

head -5 data/llm_cache.jsonl > /tmp/t && mv /tmp/t data/llm_cache.jsonl
make reproduce  # CacheMiss, exit 1

Path B — live, with AI ≈$4 · ~95 min

Needs a provider key. The model is one string, so any provider works — LiteLLM handles the routing.

cp .env.example .env   # put a key in it; .env is git-ignored
make record            # re-runs everything live

The numbers will not match the committed ones exactly — that is expected, and it is the reason Path A exists. What should hold is the shape: the baseline failing the third-party cases, the repair loop closing them.

To watch a single migration happen, with the approval gate on:

python src/migrate.py path/to/your_app.py

It prints the parity result and a diff summary, then asks. Answer n and nothing reaches disk. It also refuses outright to write over the file it read.

Main failure mode

The oracle has to run the legacy app, and most real Flask code cannot run alone

Pointed at app/case/case_misp.py from flowintel — 1017 lines, 39 routes — the static half worked perfectly and produced 171 probes. Then it recorded exactly zero responses, because the module imports flask_login and five sibling packages and expects a live database session. It is not a program; it is a fragment of one.

Stubbing those imports would mean guessing what the dependencies do, and a guessed oracle is the exact failure this project exists to avoid. So the honest statement is that this approach is strongest where migration is already easiest, and weakest on the tangled modules that are the actual reason teams stay on Flask.

The version worth building next probes a running service over HTTP rather than an imported module. Same oracle, same metric, no import problem.

Small sample of real code

Two third-party cases out of sixteen. It is the column that matters and it is thin, for the reason above.

Probes are derived, not exhaustive

They cover the parameters a handler visibly reads. A missed key costs coverage — it can never turn a failing migration into a passing one.

The agent over-inspects

On one case it burned four of eight turns and eighteen probe lookups before writing code, and invented a probe id that does not exist.

Side effects are not modelled

A handler that writes to a database is compared only on its response.

Hot take

LLM-generated tests do not verify an LLM's output. They launder it.

The test generator and the code generator share the same misreading of the requirement, so the test encodes the bug as the expectation and reports green. That is strictly worse than no verification: no verification leaves you appropriately nervous, and a passing suite makes you merge.

The rule this project is built on: an agent's verifier must draw its ground truth from something the agent cannot influence. For a migration that is easy, and almost nobody does it — the system being replaced is still running, it is authoritative, and it will answer every question you ask it.

The corollary is uncomfortable, and it is the thing worth taking to the next agent. This benchmark's baseline was right twelve times out of sixteen. Reliability at that level does not make verification less necessary — it makes it harder to justify to yourself, right up until the 3 a.m. page.
